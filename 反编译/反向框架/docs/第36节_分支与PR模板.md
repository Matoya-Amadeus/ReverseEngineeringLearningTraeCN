# Section 36: Branch / PR Template for Reverse Work

Date: 2026-03-18
Scope: <CONTENTS_ROOT>/反编译/反向框架

## Purpose
Section 36 standardizes collaboration output for reverse engineering batches, so each batch is traceable, reviewable, and replay-verifiable.

## Branch Naming
Use one branch per reverse batch:
- `codex/reverse-batch-<nn>-<topic>`

Examples:
- `codex/reverse-batch-20-live-evidence`
- `codex/reverse-batch-21-provider-signature-parity`

## Commit Template
Use scoped commits:
- `reverse(auth): <what changed>`
- `reverse(shell): <what changed>`
- `reverse(core): <what changed>`
- `docs(reverse): <what changed>`

Commit body checklist:
- Mapping file/doc touched
- Replay/contract command run
- Residual risk (if any)

## PR Title Template
`[reverse][batch-<nn>] <module>: <goal>`

## PR Description Template
- Goal:
  - What parity gap this batch closes.
- Decompiled mapping:
  - Which mapped paths/contracts are affected.
- Changes:
  - Core code changes.
  - Test/contract changes.
  - Doc/report changes.
- Acceptance evidence:
  - `node tests/auth/run-all-checks.mjs`
  - `./launcher/open-reconstructed.command`
- Risk and rollback:
  - Known non-equivalent details.
  - Safe rollback scope.

## Hard Acceptance Before Merge
1. All listed acceptance commands pass.
2. No destructive edits to decompiled artifacts.
3. Any protocol/signature delta is documented in docs.
4. New gap discovered => add follow-up checklist item.

## Notes
This section does not change runtime logic. It is a delivery governance template for keeping reverse work fast and auditable.
