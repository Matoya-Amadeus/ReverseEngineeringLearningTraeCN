## 9) V4 第一阶段：Provider 分歧图（marscode/bytedance/saas）

代码锚点：`50_反编译/10_反编译源码/电子核心/vscode-main.beautified.js`

### 9.1 Marscode Provider (`oauth/marscode/oauthService.js`)
- 位置：`38661+`
- 关键行为：
  - `getAccountUrl()` 返回 `loginHost/consoleHost/apiHost`
  - `refreshToken()` 调 `MU.getJwtToken(apiHost, refreshToken, token)` + `getUserInfo(apiHost, Token)`
  - `checkToken()` 调 `checkLogin(apiHost, token)`
  - `generateTempToken()` 支撑 JWT 临时票据链
- 结论：Marscode 是主路径，和 `tokenManager` 的 temp token 机制直接耦合。

### 9.2 Bytedance Provider (`oauth/bytedance/oauthService.js`)
- 位置：`39167+`
- 关键行为：
  - token 获取走 `POST /api/v2/GetUserToken`（header: `X-Cloudide-Token`）
  - 区域获取走 `POST /api/v2/GetUserNativeRegion`
  - `checkToken()` 当前返回固定 `{ isValid: true }`
- 结论：Bytedance 分支更像“外部 token -> 平台换取内部 token/region”的轻量适配链。

### 9.3 SaaS Provider (`oauth/saas/oauthService.js`)
- 位置：`39308+`
- 关键行为：
  - 刷新 token：`/cloudide/api/v3/trae/oauth/ExchangeToken`
  - 拉用户信息：`/cloudide/api/v3/trae/GetUserInfo`（header: `x-cloudide-token`）
  - 检查登录：`/cloudide/api/v3/trae/CheckLogin`
  - 维护 `consoleHost/apiHost` 持久化
- 结论：SaaS 分支是完整的 REST 链路，和 host 动态切换绑定最强。

### 9.4 登录统一入口与分流
- 统一入口：`loginService.login(...)`（`45121+`）
- OAuth 回调后：`this.w(t, credential)?.loginCredentialCallback(...)` 决定具体 provider 处理器
- provider 选择规则：`BYTEDANCE / MARSCODE / SAAS`（含 `SPRING/YINLI` 环境分支）

### 9.5 与 msalruntime 的关系（当前证据）
- JS 层已具备完整 oauth provider 实现，不依赖单一 native 鉴权。
- native `libmsalruntime` 同时存在完整认证能力。
- 当前阶段可判定为“多 provider + 可能按租户/环境切换到不同认证后端”的混合架构。

- country 在 `US` 列表 -> `US`

- marscode 的 storeRegion 不是静态枚举，而是由 uid+country+userTag 动态归约；这解释了其为什么依赖 TNC uid 信息。

### 25.2 核心接口签名（建议）

```ts
interface AuthProvider {
  id: 'bytedance' | 'marscode' | 'saas';
  getAccountUrl(ctx: LoginContext): Promise<AccountUrl>;
  loginCredentialCallback(payload: CallbackPayload): Promise<{ code: number; userInfo?: UserInfo; message?: string }>;
  refreshToken(refreshToken: string, current?: UserInfo): Promise<UserInfo>;
  checkToken(token: string, current?: UserInfo): Promise<{ isValid: boolean; errorCode?: string | number }>;
  refreshUserInfo?(token: string, current: UserInfo): Promise<AccountInfo>;
  generateTempToken?(token: string, current: UserInfo): Promise<{ Token: string; ExpiredAt: string }>;
}

interface AuthOrchestrator {
  login(provider?: string, extra?: { email?: string; customDomain?: string }): Promise<UserInfo>;
  getUserInfo(): Promise<UserInfo | undefined>;
  logout(force?: boolean): Promise<void>;
}
```

### 25.3 最小调用顺序（先跑通）

1. IPC `invoke-login`
2. `AuthOrchestrator.login` -> `ProviderRegistry.getProvider`
3. 启本地 callback server
4. 拼登录 URL 并 `openBrowser`
5. callback 到达 -> `provider.loginCredentialCallback`
6. `setUserInfo` + broadcast

B. 刷新：
1. timer/resume -> `TokenManager.verifyTokenInBackground`
2. `provider.refreshToken`
3. 成功回写 userInfo

2. 再接 `marscode` provider（因为逻辑最复杂）
3. 接 `TokenManager` 强退分支
4. 最后接 `StoreRegion/TNC` 自愈链

- 能登录、能刷新、能在 token 无效时强退、能返回 region（marscode 缺字段时可先 UNKNOWN）。

## 27) 按顺序继续：Provider 反推矩阵（JU / cS / XU）

目标：
- 明确三 provider 的“相同接口 + 不同语义”，避免后续把 marscode 逻辑误套到 bytedance/saas。

### 27.1 统一接口面（代码层必须同构）

从反编译可归纳的公共能力：
1. `getAccountUrl()`
2. `refreshToken(refreshToken, currentUser?)`
3. `loginCredentialCallback(callbackPayload)`
4. `checkToken(token, currentUser?)`

扩展能力（非全部 provider 都有）：
5. `refreshUserInfo(token, currentUser)`
6. `generateTempToken(token, currentUser)`

### 27.2 bytedance: `JU`（最轻实现）

锚点：`vscode-main.beautified.js` 约 `39167+`

特征：
1. `checkToken()` 直接返回 `{ isValid: true }`（无严格校验远端分支）。
2. `refreshToken()` 核心是解析 token payload + 调 `GetUserToken`/`GetUserNativeRegion`。
3. account 固定 `scope=BYTEDANCE`，region/tag 由包类型与默认值决定。

反推建议：
- 先把 bytedance 当成“最小 provider 基线”，用于验证 orchestrator 与 registry。

### 27.3 marscode: `cS`（最重实现，优先反推）

锚点：`vscode-main.beautified.js` 约 `38661+`

特征：
1. `refreshToken()`：`getJwtToken + getUserInfo + _updateByOriginUserInfo`。
2. `_updateByOriginUserInfo()`：
- 先校验 `current userId` 一致，不一致抛 `OauthService:UserInfoNotMatchError`。
- spring/i18n 路径下调用 `getStorageUserTag + tryReUpdateUserToTnc + buildStoreRegionByUidCountry`。
3. `refreshUserInfo()`：用于补齐 account（被 TokenManager 在 region 缺字段时调用）。
4. `checkToken()`：真实远端校验，失败将触发上层强退。
5. `generateTempToken()`：给 TokenManager 写临时 jwt 文件使用。

反推建议：
- 先完成 cS 的最小真逻辑，再让其它 provider 对齐接口。

### 27.4 saas: `XU`（中等复杂度）

锚点：`vscode-main.beautified.js` 约 `39308+`

特征：
1. `loginCredentialCallback()` 会保存 host 信息（`consoleHost/apiHost`）再换 token。
2. `refreshToken()` 走 `/oauth/ExchangeToken`；命中特定错误码映射 `RefreshTokenInvalid`。
3. `refreshUserInfo()` 从用户信息接口重建 account（tenant/role/privacy 等字段）。
4. `checkToken()` 独立实现，不与 bytedance 共用简化路径。

反推建议：
- 把 host 持久化抽成独立小模块，避免污染主编排。

### 27.5 Provider 差异对 TokenManager 的影响

1. `checkLoginToken` 强退判定：
- bytedance 风险低（总是 valid）；
- marscode/saas 才是 strict-check 主要来源。

2. `refreshStoreCountryCode`：
- 只对 `scope=MARSCODE` 生效；
- 依赖 provider 的 `refreshUserInfo`。

3. `refreshTempToken`：
- 当前实现复用 marscode provider 能力（`generateTempToken`）。

### 27.6 反推实施顺序（provider 维度）

1. 先 `JU`：验证编排链通路。
2. 再 `cS`：落地 TNC/region/strict-check 主体。
3. 后 `XU`：补齐企业租户字段与 host 持久化。

结论：
- provider 层的关键不是“接口多少”，而是 `cS` 的一致性校验与 region 自愈链；它决定整体行为是否接近原应用。

// token-manager.ts
import { CH } from '../types/auth-events';
import type { AuthProviderId, UserInfo } from '../types/auth-types';
import { ProviderRegistry } from '../providers/provider-registry';

export class TokenManager {
  private refreshTokenPromise?: Promise<UserInfo>;

  constructor(
    private readonly providers: ProviderRegistry,
    private readonly onForceLogout: () => void,
    private readonly broadcast: (channel: string, payload?: unknown) => void
  ) {}

  verifyTokenInBackground(user?: UserInfo): void {
    void user;
  }

  async refreshUserInfoByToken(refreshToken: string, scope: AuthProviderId, current?: UserInfo): Promise<UserInfo | undefined> {
    const p = this.providers.getProvider(scope);
    if (!p) return undefined;
    if (!this.refreshTokenPromise) this.refreshTokenPromise = p.refreshToken(refreshToken, current).finally(() => (this.refreshTokenPromise = undefined));
    try {
      return await this.refreshTokenPromise;
    } catch (e: any) {
      if (String(e?.message || '').includes('RefreshTokenInvalid')) this.onForceLogout();
      return undefined;
    }
  }

  async checkLoginToken(user: UserInfo): Promise<void> {
    const p = this.providers.getProvider(user.account.scope);
    if (!p) return;
    const result = await p.checkToken(user.token, user).catch(() => ({ isValid: true }));
    if (!result.isValid) {
      this.onForceLogout();
      this.broadcast(CH.MAIN_TO_SANDBOX_SHOW_AUTH_INVALID_DIALOG, { errorCode: result.errorCode });
    }
  }

  async handleForceRefreshUserInfo(_force?: boolean): Promise<void> {}

  setJwtTokenEnabled(_enabled: boolean): void {}
}

// auth-watch-service.ts
import type { UserInfo } from '../types/auth-types';

export class AuthWatchService {
  private timer?: ReturnType<typeof setInterval>;

  constructor(private readonly check: (user: UserInfo) => Promise<void>) {}

  start(user?: UserInfo, intervalMs = 0): void {
    this.stop();
    if (!user || intervalMs <= 0) return;
    this.timer = setInterval(() => {
      void this.check(user);
    }, intervalMs);
  }

  stop(): void {
    if (this.timer) clearInterval(this.timer);
    this.timer = undefined;
  }
}

## 35) 按顺序继续：首轮提交策略（commit 粒度与回滚点）

目标：
- 让源码重建过程“可持续提交、可快速回滚、可定位回归”。
- 每个 commit 对应一个明确能力点，避免跨层混改。

### 35.1 提交粒度原则

1. 单提交只覆盖单层责任
- 类型层、IPC 层、token 层、region 层、测试层不要混在同一个 commit。

2. 单提交必须可编译
- 即使功能未全，也要保持主分支可运行/可测试。

3. 单提交必须可回滚
- 回滚后不应留下“半接线”状态（例如 IPC 常量存在但 handler 不存在）。

### 35.2 推荐 commit 序列（首轮）

1. `feat(auth): add base auth types and channel constants`
- 范围：`auth-types.ts` + `auth-events.ts`
- 回滚点：删除类型与常量文件，不影响运行时逻辑。

2. `feat(auth): add provider registry with marscode fallback`
- 范围：`provider-registry.ts`
- 回滚点：回退后主链仍可由 mock provider 直接注入。

3. `feat(auth): scaffold orchestrator and auth ipc handlers`
- 范围：`auth-orchestrator.ts` + `auth-ipc.ts`
- 回滚点：回退后仅失去新 IPC 接线，不影响旧实现。

4. `feat(auth): implement token manager force-logout core path`
- 范围：`token-manager.ts`
- 回滚点：回退后恢复“无强退策略”的骨架状态。

5. `feat(auth): add auth watch scheduler with interval reconcile`
- 范围：`auth-watch-service.ts`
- 回滚点：回退后只丢失 strict-check 定时能力。

6. `feat(auth): add user storage and setup-login-failed consume path`
- 范围：`user-storage.ts` + orchestrator 消费逻辑
- 回滚点：回退后仅影响本地恢复/一次性状态消费。

7. `feat(auth): add region and tnc self-heal services`
- 范围：`store-region-service.ts` + `tnc-region-service.ts`
- 回滚点：回退后 region 恢复为静态策略。

8. `test(auth): add offline fixtures and replay scenarios`
- 范围：`tests/fixtures/auth/**` + `tests/auth/*.spec.ts`
- 回滚点：仅移除测试资产，不影响运行逻辑。

### 35.3 每次提交前的风险闸门

1. 编译闸门
- 类型错误为 0。

2. 行为闸门
- 至少跑对应层的最小测试：
  - token 提交至少跑强退两例（refresh invalid / strict invalid）。
  - region 提交至少跑 UNKNOWN->UID 自愈例。

3. 接口闸门
- 事件名与第28/29节保持一致，禁止临时改 channel 字符串。

4. 观测闸门
- 新增错误路径必须带 provider/action/errorCode 日志。

### 35.4 回滚策略（出问题时）

1. 只回滚最近“责任单一”的一个 commit。
2. 回滚后立即重跑该层最小测试，确认恢复。
3. 记录失败模式到文档（推荐新增 `00_文档/00_总览/ROLLBACK_NOTES.md`）。

### 35.5 禁止操作（首轮）

1. 禁止跨 3 个以上模块的大提交。
2. 禁止“修 bug 顺手重构”式提交。
3. 禁止在同一次提交里同时改 IPC 名称与业务逻辑。

结论：
- 35节完成后，反推实现进入“工程化可控”阶段；下一步第36节建议补“分支策略与PR模板（如何审阅每个里程碑）”。

## 36) 按顺序继续：分支策略与 PR 模板（审阅与协作用途）

用途：
- 不是技术实现层，而是“交付治理层”。

### 36.1 分支策略
